## Product Overview

**Working one-liner, for context rather than publication:** Temperance Engine is a configurable AI operator system that connects a defined work loop, project context, relevant skills, routing and verification across selected AI coding clients.

**What it does:** It packages portable instruction/runtime components and setup tooling around coding clients. PAI supplies the work method; configured skill clusters discover and load relevant procedures; optional GSD provides a planning backbone; OmniRoute owns model/provider routing. Project criteria and verification preserve a way to judge the result. A selected personal or company profile supplies optional bindings rather than making the founder's setup a core dependency.

**Category:** AI operator system. Explain this category immediately in practical terms; it is a positioning choice, not a claim of an established market taxonomy. “Shared operating layer for AI coding tools” is a useful supporting description when followed by the actual workflow.

**Product type:** Public source, local configurable operator/runtime package with installer, guided onboarding, optional host/client integrations and external dependencies. Remote calls depend on the selected setup.

**Business model:** Public source is available for evaluation. No verified pricing, paid plan, support entitlement or revenue model is supplied. Do not invent one.

## Target Audience

**Primary audience:** Developers and technical operators who already use more than one of Codex, Claude Code, Cursor and OpenCode, and are responsible for project instructions, selected capabilities and checking changes. Tool names orient the audience; they do not promise identical integration depth.

**Target teams:** Solo technical builders and small development teams with a person willing to inspect and configure local tooling. Industry, team-size ranges, adoption and willingness to pay remain unresearched.

**Decision-makers:** The developer/operator trying the setup; a technical founder or team lead may sponsor shared practice. No enterprise buying committee or financial buyer is established.

**Primary use case:** Give a coding project a deliberate operating workflow around the agents already being used.

**Jobs to be done:**

- When I move between coding clients or return to a project, help me work from explicit project context and criteria so I can determine what should happen next. Do not imply automatic native-chat migration or lossless session continuity.
- When a task needs specialist knowledge, help me discover and load a relevant procedure, then scope the work and verification around it rather than treating a catalog as expertise already invoked.
- When I delegate or route a piece of work, help me distinguish the selected capability, actual attempt and checked outcome so I can decide whether the change meets the project goal.

**Concrete illustrative scenario:** A keyboard-search improvement. Inspect current behavior and project criteria; select the design/testing skill; plan the scoped component change; build it through an authorized client; run relevant checks; verify keyboard behavior; propose a reusable lesson. This is a teaching example, not a customer case study.

## Problems & Pain Points

**Core problem:** Coding clients can produce work, while the operating choices around the work—what context to use, which procedure to follow, what to delegate, where to route, and what counts as checked—still need an explicit owner and method.

**Status quo friction:** Separate per-client instructions, copied prompts, an unstructured skill folder, manual model selection and ad hoc checking can leave the workflow implicit. This is a plausible evaluation contrast, not measured customer behavior or a claim that any named client lacks these features.

**Cost:** No measured time, money or defect reduction is available. Explain the activities the visitor must otherwise coordinate; do not translate them into invented savings.

**Emotional tension:** Wanting useful agent assistance while still understanding and owning the result. Treat this as an inferred tension, not a verbatim customer finding.

## Competitive Landscape

**Direct competitors:** Not researched. No defensible comparative feature table or superiority claim is available.

**Secondary alternatives:** Configure project instructions, workflow/skill packs, planning tools and a gateway independently. These may be sufficient for many users. Temperance's proposed value is the defined composition and setup around them, not ownership of their capabilities.

**Indirect alternatives:** Stay with one coding client and a personal checklist; keep coordinating prompts and checks manually. Do not caricature those choices as careless or incapable.

**Contrast to establish:** A coding client performs work; Temperance provides a configurable operating method around selected clients. A skill supplies a procedure; a gateway routes requests; a profile binds host context. Temperance should explain how those jobs connect without pretending to replace their owners.

## Differentiation

**One key promise:** Give a coding project a defined way to move from relevant context through selected skills and routed work to a result the operator can check, while choosing the clients and profile bindings that fit the host.

**Supporting reasons to believe:**

- A seven-phase PAI loop connects observation, reasoning, planning, construction, execution, verification and learning.
- Configured skill-cluster discovery and lazy loading connect task needs with procedures without loading an entire catalog at startup.
- Public setup supports selected instruction surfaces and optional client integrations rather than requiring one vendor account or the founder's private profile.
- OmniRoute remains the owner of credentials, model inventory and fallback, while project planning and acceptance remain with their existing owners.
- Public composition/lifecycle and the new bounded process/orientation source give inspectable contracts. Source presence remains distinct from host installation and acceptance.

**Why that could matter:** The operator can understand the path through the work and configure its parts deliberately. This is a proposed benefit grounded in mechanism, not a proven productivity outcome.

**Custom agents in this story:** Specialist roles can perform scoped writing, implementation or review when the selected client supports them. The public PAI flow names subagent-driven work and bounded parallel dispatch as tools called by the workflow. Do not claim all clients ship an identical agent fleet, that every custom agent is bundled, or that specialist instructions create expertise/acceptance by themselves. This editorial process uses real scoped custom agents; that process attribution is separate from portable product availability.

## Objections

| Likely objection, not a recorded sales quote | Evidence-led response direction |
| --- | --- |
| “Is this another agent or another model?” | Explain the operating layer around selected clients, with one real task connecting context, skill, work and checking. |
| “Why not use my client's project instructions?” | Acknowledge that can be enough. Show the additional composition of a work loop, skill discovery, routing and verification rather than asserting a feature deficit in the client. |
| “Will I have to adopt the founder's whole setup?” | Start from the portable core; personal/company profiles are optional. Selected integrations still have prerequisites. |
| “Will it change my configuration or send my data away?” | Show the installer dry run, backup/recovery path and integration-specific data flow. Do not promise installation has no effects or that remote inference is offline. |
| “Are these organs working features today?” | Name advisory roles as architecture, state the read-only Vestibule source preview and other concrete adapters' development status in the appropriate availability explanation. |
| “Can it verify that everything is done for me?” | Explain project criteria and appropriate tool checks. A completed process, test fixture or health response does not itself establish acceptance. |

**Anti-personas:** A visitor seeking a hosted autonomous workforce, a new foundation model, a guaranteed zero-configuration setup, an enterprise compliance certification, or an instant upgrade to every client's capabilities. None is supported by the evidence.

## Switching Dynamics

**Habit:** Existing client instructions, familiar model choices and individually useful tools may already work well enough.

**Anxiety:** Installation effects, overlapping tools, private-data access, unsupported client hooks, setup effort and whether architectural language hides unfinished adapters.

These are hypotheses to validate, not recorded conversion research.
